## 範圍、風險與策略

優先驗證「合法提交 → 後端計算與存檔 → 只見所選員工的待審核假單」，以及「驗證拒絕 → 資料不變」。以 API 驗收確認實際接通資料庫；只有天數與理由處理加必要純函式單元測試，畫面回饋與連點、網路中斷交由人工驗收。不固定湊滿測試層級。

- 高風險：日期／半天計算錯誤，可能存錯天數；API 加固定答案的單元案例驗證，TC-04～06，FR-03、04。
- 高風險：非法輸入存檔或信任客戶端狀態／天數；直接呼叫 API 繞過畫面，核對資料前後一致，TC-03、07、08、10，FR-01、02、05、08。
- 高風險：混入他人資料、資料僅存在頁面；用 A／B／C 與 app 重建核對，TC-02、09，FR-09、10、NFR-02。
- 高風險：已提交卻誤告未存、自動重送造成重複；以可控制故障替身與人工網路案例驗證，TC-11、人工 M-03／05／06，FR-06、07。
- 高風險：使用者文字被當 HTML 或 SQL；API 文字往返、畫面與程式審查共同驗證，TC-12、NFR-01，單一惡意字串不代表完整安全證明。
- 中風險：理由長度前後端不一致；TC-07 及人工核對特殊字元，FR-02。
- 測試配置風險：碰到開發資料庫或依賴真實日期；全部自動化使用暫存檔、明確種子及固定時鐘，NFR-03。

### 已採用的取捨與延後範圍

本計畫為 **12 個 TC 群組，內含分別執行的變體，不是 12 次請求或 12 個斷言**。不將任一變體未執行的群組標為全部通過。

完整 400／415／405 協定錯誤矩陣、多重錯誤全部優先序組合、極端日期、資料庫損毀恢復與所有並行情境尚未完整覆蓋；效能亦未量測。使用者已採用延後範圍，仍由講師在實作前確認課堂可接受性；未確認不得宣稱全部 SDS 契約已驗證。若要求補齊，增加明列子案例或調整預算，不以改規格或刪必要測試達成數量限制。

無主管核准、額度、登入、部署或 LLM 功能，本次不建立模型 eval、模型注入評測或其占位章節。TC-12 的 SQL／HTML 文字安全是主線應用安全，不是模型評測。

## 環境、資料與判定方式

- 目標：Windows、Python 3.12、pytest、httpx／FastAPI TestClient；依課程 constraints 安裝。實際 Windows／Python 3.12.10 與套件版本見 001 證據，不沿用教材結果當本專案通過證據。
- 實際執行指令：在根目錄使用 `.venv\Scripts\python.exe -m pytest`；不假設 shell 已啟用 venv。
- 每個獨立案例／參數變體用新的 tmp_path SQLite 檔案；明確注入 A＝1／員工A、B＝2／員工B、C＝3／員工C，初始假單為零。需要預存資料的案例自行明確建立，且保存已知輸入與預期，不依賴開發資料庫。
- `create_app(db_path=暫存絕對路徑, today_provider=固定回傳2026-10-14的函式, seed_employees=明確名單)`；TestClient context 啟閉 lifespan。TC-02 特別在同一暫存檔重建 app。測試不得讀寫 `backend/data/leavebot.db`。
- 基準提交：A、annual、2026-10-12 至 2026-10-12、full、理由留空。各案例只改指定欄位，其餘合法。
- 預期答案來自 SRS／SDS 與已審人工算例，寫成固定值；不得呼叫 calculate_day_units、normalize_reason 或其他被測函式產生預期值。單元測試呼叫它們取得的是「實際結果」。
- 每個成功核對 HTTP、JSON、保存欄位、天數、pending 及筆數；每個驗證拒絕核對 HTTP、code、field、message 與完整假單資料不變。用獨立 sqlite3 查詢核對保存值，不只相信 API 回應。
- 通用錯誤必須符合 SDS 的 `{"error":{"code":...,"message":...,"field":...}}`；未知提交結果不是驗證拒絕，不套用「資料必定不變」斷言。
- 業務自動測試標記 `@pytest.mark.req("TC-xx", "對應 AC/FR 編號")`，依測試真正斷言標記；不能只加 marker 就算覆蓋。以下路徑皆為未建立的預定位置。

### TC-07｜理由選填、邊界與碼位（AC-02.2；FR-02、08；NFR-02）

以下為 002 已由使用者確認的新預期，全部新建／修訂部分**未執行**；各變體使用合法基準請求。先新增獨立 101 拒絕測試，確認舊實作回 201 的紅燈，再依票執行，不用被測函式計算答案。

- 「假」重複 100 次：201，保存恰好 100 碼位；101、200、201 次分別：422 REASON_TOO_LONG、field＝reason、message＝「理由最多 100 字」，假單全資料前後不變，不只檢查筆數。
- ` 請 假 `：201，保存 `請 假`，3 碼位；只含空白、省略 reason、reason＝null 分別測：201，各保存 `""`。
- 😀、e 加 U+0301、👩‍💻：分別 1、2、3 碼位，原組合不正規化；各可保存。
- 必要單元以固定整數／字串核對上述碼位及處理結果；API 核對特殊字元往返與邊界拒絕，不能只測單元就宣稱有後端拒絕。
- 補單元：100 可回原文、101 拋 REASON_TOO_LONG；另以輸入兩端空白＋100 碼位，確認先去空白再判長度。上述常數為人工指定，不呼叫 normalize_reason 當答案來源。
- 舊資料相容性：在獨立暫存 DB 用明確固定資料建立一張理由為「假」重複 200 次的歷史申請（可由 schema fixture／參數 SQL 建立，不能用新 POST 假裝舊提交成功）；記錄完整資料快照。啟動、查 A 列表、關閉並重建 app 再查，均回原理由、原 id／欄位，DB 全資料不變；新 POST 同樣 200 碼位仍應拒絕。這同時承接 AC-03.1、FR-09、NFR-02，不增加第 13 個 TC 群組。

空白集合依 SDS，不使用另一套 trim 偷改答案；本組算例不宣稱每個空白字元已測遍。狀態：002 邊界與相容性未執行；空白／特殊字元等 001 歷史結果保留，但仍須在 002 回歸。現有 test_leave_validation.py 的「200 成功」期待已失效，待實作時依本次人確認改為拒絕；201 拒絕仍有效，訊息須同步。

### TC-11｜資料庫故障與結果未知（FR-05、08；NFR-02；SDS 錯誤契約）

在可控制的資料存取／交易接縫使用替身，不破壞開發 DB，不依真實磁碟損毀製造故障。

- 模擬列表讀取失敗：503 DB_UNAVAILABLE，field＝null，不能回 200 空列表；假單資料不變。
- 在 INSERT 已發生但 commit 前模擬寫入故障：503 DB_UNAVAILABLE；rollback 後以獨立連線核對資料與原先一致，證明沒有殘留插入。
- 模擬 commit 結果未知：503 SUBMISSION_UNKNOWN、field＝null，message 為 SRS 指定先查看假單的提示；不把未知結果斷言為零新增，不自動重送。

所有回應不得含 SQL、堆疊、本機 DB 路徑或理由。這驗證處理分支，不代表已驗證硬體斷電復原。狀態：2026-11-01 已執行通過，見 001 執行證據；不代表未列出的變體已覆蓋。
